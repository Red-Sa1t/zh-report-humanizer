# 报告语体改写范例

本文件全部采用**平实语体**：学生写完实验后交给老师的报告该有的样子。

平实语体的三条底线：句子直陈、词用常见的、不修饰文字。
报告读起来像不像人写的，主要取决于内容（关键数字、真实过程）。

---

## 范例 1：从抽象到具体

**AI 腔：**
> 通过本次扫描，工具对目标项目的许可证状况进行了较为全面的检测，整体检测覆盖率较高，绝大多数源文件均被成功识别。

问题：前半句「工具对…进行了较为全面的检测」只描述了动作，读完不知道结果；后半句「覆盖率较高，绝大多数源文件被识别」是一个判断，但没有数字支撑。

**平实写法：**
> 本次扫描的覆盖率较高，源码文件全部检出了许可证。698 个文件中有 628 个检出许可证，覆盖率为 90.0%；没有检出的 70 个文件都是 `.bin`、`.txt`、`.zip` 和图片这类非源码文件，各类数量见表 3-1。

第一句是概括，读者先拿到结论；后面的数字用来核对它。原句里的「较高」留下了，因为后面紧跟着 90.0% 这个数字。各类文件的具体数量（`.bin` 35 个、`.txt` 21 个……）放进表格，正文只说它们都是非源码文件，因为这才是读者需要的判断。

**改过头的写法：**
> 本次扫描共检测 698 个文件，其中 628 个检出许可证，覆盖率为 90.0%。没有检出的 70 个文件中，`.bin` 35 个、`.txt` 21 个、`.zip` 6 个……

只有数字、没有概括，读者要自己从一串数里归纳结论，读起来很累。具体性要有，数字的作用是支撑结论。

## 范例 2：写出真实过程

**AI 腔：**
> 在安装过程中遇到了一些网络相关的问题，通过调整配置最终成功完成安装。

问题：把一段有信息的排查过程压缩成了一句废话。

**平实写法：**
> 安装 ScanCode 时反复失败，原因是网络在传输大文件时不稳定，换成有线网络后才装上。排查过程如下。
>
> 执行 `pip install scancode-toolkit` 时连续 5 次失败，报错为 `SSLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING]'))`，错误指向 pypi.org 的 443 端口。
>
> 我最初认为是下载源的问题，于是改用清华 TUNA 镜像源。改用后 SSL 握手可以正常完成，也能正常读取索引，但主文件下载到约 34 MB 时出现 `ReadTimeoutError`。把超时时间改为 60 秒、重试次数改为 10 次后，仍然在同一位置失败。多次失败位置相同，放宽超时设置后仍然失败，所以问题出在网络连接传输大文件时不稳定。最后更换了网络连接方式。

第一段用一句话交代结果和原因，读者如果只关心"装上没有、为什么慢"，读到这里就够了；想看排查细节的再往下读。

## 范例 3：结论要有，但不要拔高

**AI 腔：**
> 总体来看，该项目的许可证合规状况良好，工具检测结果令人满意。

问题：「良好」「令人满意」都是评价，后面的数据没法核对，结论也没有说明在什么条件下成立。

**平实写法：**
> 从检测结果看，Commons-IO 的许可证情况比较清楚：571 个 Java 源文件全部检出 apache-2.0，与 `pom.xml` 中的声明一致，版权集中在 `NOTICE.txt` 中。
>
> 这个结论有两个限制。第一，ScanCode 只扫描仓库中实际存在的文件，不处理依赖关系，所以它只能说明仓库自身没有声明冲突。第二，工具输出的是检测结果，许可证之间的兼容性还需要人工判断。

## 范例 4：不要写金句

这是最容易改过头的地方。下面左边看着"有人味"，其实是文风表演。

| 金句化（不要写） | 平实写法 |
|---|---|
| 这个坑比前两个值钱 | 这个问题的影响比前两个大 |
| 麻烦的地方在于退出码是 0 | 这次扫描的退出码是 0 |
| 工具没报错，它只是什么都没扫 | 工具没有报错，但也没有扫描任何文件 |
| 这两件事之间隔着一次人工判断 | 这部分需要人工分析 |
| 分母需要说明一下 | 统计范围需要说明 |
| 结论的适用范围比看上去窄 | 这个结论有两个限制 |
| 这里有个坑 | 这里出现了一个问题 |

**判断方法**：这句话像不像一个本科生在实验报告里会写的？如果像公众号推文，就是过头了。

| AI 腔 | 平实写法 |
|---|---|
| 该工具不仅能够识别许可证，更能够检测版权信息 | 工具可以同时检测许可证和版权信息 |

## 范例 6：不要制造节奏

**刻意起伏（不要写）：**
> 工具的流程是扫文件、识别许可证、提取版权，最后输出结构化结果。真正耗时间的是第一步。很慢。

问题：为了"节奏"硬插一个两字短句。这是刻意为之。

**平实写法：**
> 工具的处理流程是扫描文件、识别许可证、提取版权声明，最后输出结构化结果。整个过程用时约 124 秒，其中扫描本身占 120 秒。

句子长短接近完全没有问题。**直接陈述是这类报告的正常写法。**

## 范例 7：否定与肯定对举必须删掉一半（硬规则一）

这是四条硬规则里的第一条，没有例外。下面每一条都同时写了否定和肯定，先否定再肯定、先肯定再否定都算，必须删掉一半，二选一。

| 原文（禁止） | 改法 A：只写否定 | 改法 B：只写肯定 |
|---|---|---|
| 这次失败的原因不是超时，而是网络不稳定 | 这次失败与超时设置无关 | 失败的原因是网络在传大文件时不稳定 |
| 工具没有报错，而是直接跳过了该目录 | 工具没有报错 | 工具直接跳过了该目录 |
| 这不只是速度问题，更是数据问题 | 只留否定信息太少，不推荐 | 这影响到数据本身 |
| 与其说是误报，不如说是阈值太松 | 这个结果与阈值有关 | 阈值设得太松 |
| 问题不在工具，则在于输入数据 | 工具侧没有问题 | 输入数据不规范导致的 |
| 这里没有报错，恰恰说明它什么文件都没扫 | 这里没有报错 | 这次扫描没有处理任何文件 |
| 问题出在网络上而不是工具上 | 工具侧没有问题 | 问题出在网络上 |
| 这是网络问题，不是配置问题 | 和配置无关 | 是网络问题导致的 |
| 准确率的提高来自数据，不来自模型容量 | 准确率的提高和模型容量无关 | 准确率的提高来自训练数据分布的扩展 |

改法 A 和改法 B 都成立，选信息量大的那一个。多数情况下 B 更好，因为结论本身比"排除了什么"有用。

改完之后，一句话里如果还有肯定和与它对举的否定（「不是…而是…」「而不是」「不来自」等），就说明还没改完。

## 范例 8：过程陈述不用箭头（硬规则二）

**AI 腔：**
> 整个处理流程是读取文件 → 解析 AST → 抽取许可证 → 输出 JSON。

问题：四步之间的连接关系全部省略，读者看到的是流程图的文字版。

**平实写法 A（关联词串起来）：**
> 整个处理流程从读取文件开始，然后解析 AST，再到抽取许可证，最后输出 JSON。

**平实写法 B（环节较短时用顿号）：**
> 处理流程是读取文件、解析 AST、抽取许可证、输出 JSON。

代码块和行内代码里的箭头照常写，下面这条是合法的：

```c
/* head->next 里的 -> 是代码，不在检查范围内 */
struct Node *p = head->next;
```

## 范例 9：破折号换掉（硬规则三）

| 原文（少用破折号） | 平实写法 |
|---|---|
| 工具只扫描仓库中实际存在的文件——不处理依赖关系 | 工具只扫描仓库中实际存在的文件，不处理依赖关系 |
| 结论只有一个——全是误报 | 结论只有一个：全是误报 |
| 这次检测覆盖了全部源文件——共 571 个 | 这次检测覆盖了全部源文件，共 571 个 |

引文原文里的破折号照引不改，专有名词和表格空值占位也不算。

## 范例 10：把流水句压成单句（正向手法）

这一类句子不违反四条硬规则中的任何一条，自检脚本也不会把它算成禁用项，但它读起来像 AI 列的清单：四个以上小句靠逗号并排，主干不清。

**AI 腔（流水句）：**
> 图片压缩与预处理，手机拍的原图一张 3 到 5 MB，压缩到 500 KB 以内再上传，跨网传输量能降一个量级。

**三个手法一起用：**

- **降级**：挑「压缩」当主干，其余小句降成句子成分
- **显性化**：补一个「以」，把「压缩」和「降低传输量」之间的目的关系写出来
- **去情态**：删掉「能」，顺手把「降一个量级」换成「大幅降低」

**改后：**
> 图片压缩与预处理：将手机拍的原图从 3 到 5 MB 压缩到 500 KB 以内再上传，跨网传输量大幅降低。

「降一个量级」是 AI 偏爱的说法。这句话前面已经写了「3 到 5 MB」和「500 KB」，读者能自己算出倍数，结果部分用「大幅降低」概括就够了。要留住的是前面那两个数字，有了它们，「大幅」才有依据。

**不要压过头：**

| 改过头 | 问题 |
|---|---|
| 图片压缩与预处理，例如将手机拍的原图一张 3 到 5 MB 压缩到 500 KB 以内以降低跨网传输量 | 「例如」用错；「以内以」连读拗口；「再上传」被压掉 |
| 图片压缩与预处理，压缩原图以大幅降低传输量 | 具体数字全丢，「大幅」失去了依据，等于把正向信号删掉了 |

**什么情况下用**：条目、要点这类需要紧凑表达的地方用得最多。正文叙述里流水句读得顺，可以不动，这一节不是给流水句定罪。

## 范例 11：去掉 emoji 标记（硬规则四）

**AI 腔：**
> ✅ 安装完成
> ✅ 扫描完成，共 698 个文件
> ⚠️ 70 个文件未检出许可证
> 🚀 后续可优化扫描速度

**平实写法：**
> 安装和扫描都已完成，共扫描 698 个文件，其中 70 个没有检出许可证（明细见表 3-1）。扫描用时 123.97 秒，其中 120.03 秒花在文件扫描上，这一步是后续优化的重点。

emoji 列表改回句子之后，四条之间的关系（哪个是结果、哪个是问题、哪个是下一步）才写得出来。

## 自查口径

改完后按顺序检查两件事：

1. **每一段有没有具体的东西？**（数字、文件名、命令、报错原文）数据多的段落，开头有没有一句能被这些数据核对的概括（见范例 1）？
2. **有没有写出"我原本以为…结果…"这样的真实过程？**

两条都满足，就不要再改文字了，语言保持平实即可。

另外单独做一次句式与标点检查：

1. 搜索「而是」「则是」「更是」「而不是」「而非」「不来自」，同一句里肯定和否定对举的，删掉一半（见范例 7）。
2. 搜索 `→` 和 `->`，代码块之外的过程描述改成关联词或顿号（见范例 8）。
3. 搜索 `——`，换成逗号、括号或冒号（见范例 9）。
4. 删掉所有 emoji 和装饰符号（见范例 11）。

这四条都是硬规则，没有例外。自检脚本会逐项列出命中位置。

最后再做一次正向手法的挑选（见范例 10）：自检脚本报出的「可能性表述」和「逗号过多的流水句」只是候选清单，读得顺的句子可以不改。挑主干不清、逻辑关系要猜的句子做降级和显性化，压的时候把过程步骤和具体数字留住。
